# Release 阻断问题审查清单

本文档整理当前已识别的上架阻断、上架前必修和后续质量问题，用于指导发布前修复顺序。

## 总结

当前真正阻止上架的是两项：

1. `loadPhotos()` 缺少异常处理，异常时 UI 可能永久卡在 Loading。
2. 缺少隐私政策 URL，Google Play 上架表单无法通过。

建议同步处理 Android 10 删除路径问题。否则 API 29 用户可能无法删除照片，即使不一定直接阻止提审，也会造成核心功能不可用。

## 优先级总览

| 优先级 | 数量 | 定义 | 发布建议 |
| --- | ---: | --- | --- |
| P0 | 2 | 阻止上架或导致应用核心流程不可用 | 必须先修 |
| P1 | 2 | 上架前必须修，影响核心功能或可调试性 | 建议随 P0 同步修 |
| P2 | 4 | 质量、隐私、测试和体验问题 | 上架前尽量修，最晚进入后续 hardening |
| P3 | 2 | 后续迭代优化 | 可排期 |

## P0 — 阻止上架

### P0-1：`loadPhotos()` 无异常处理

**位置**：`PhotoViewModel.kt`

**现状**：

`loadPhotos()` 在 `viewModelScope.launch {}` 内执行照片加载逻辑，但外层没有 `try/catch`。

**风险**：

权限异常、IO 异常、MediaStore 查询异常都可能直接中断协程。用户看到的结果是页面一直停在 Loading，不知道发生了什么，也无法恢复。

**为什么是 P0**：

这是首屏核心路径。只要照片加载失败没有被转成明确 UI 状态，应用就可能在真机上表现为“打不开相册”。

**修复建议**：

- 在 `viewModelScope.launch` 内包裹 `try/catch`。
- 捕获异常后写入明确的错误状态。
- Loading 必须在成功和失败路径都能结束。
- 失败时 UI 给出可理解提示，例如权限异常、读取失败、请重试。
- 保留日志，方便定位具体设备和系统版本问题。

**验收标准**：

- 权限被拒绝时不会永久 Loading。
- MediaStore 查询抛异常时不会崩溃。
- UI 能展示错误态或空态。
- 用户重新授权或重试后可以重新加载。

---

### P0-2：隐私政策缺失

**位置**：发布材料 / Google Play Console

**现状**：

项目涉及照片权限和媒体访问，但还没有可用于上架表单的隐私政策 URL。

**风险**：

Google Play 对涉及敏感权限和用户数据访问的应用要求填写隐私政策。缺少隐私政策 URL 会直接导致提审失败或被拒。

**为什么是 P0**：

这不是代码问题，但会直接阻止上架。

**修复建议**：

- 编写一份简单、真实、可公开访问的隐私政策。
- 内容至少覆盖：
  - 应用访问照片的目的。
  - 是否上传照片。
  - 是否收集个人信息。
  - 是否与第三方共享数据。
  - 数据保留策略。
  - 用户联系方式。
- 将隐私政策部署到稳定 URL。
- 在 Google Play Console 中填写该 URL。

**验收标准**：

- 隐私政策 URL 可公开访问。
- 内容与应用实际行为一致。
- Play Console 上架表单已填写并保存。

## P1 — 上架前必须修

### P1-1：Android 10 删除路径处理不正确

**位置**：`deleteDirectly()`

**现状**：

API 29 + targetSdk 35 下 scoped storage 已生效。直接调用 `contentResolver.delete()` 删除他人媒体文件时，系统可能抛出 `RecoverableSecurityException`。当前代码 catch 了宽泛的 `Exception`，失败会被吞掉，用户只看到照片删不掉。

**风险**：

Android 10 用户删除功能可能完全不可用，而且没有日志可查。

**为什么是 P1**：

删除是应用核心功能。虽然不是所有设备都会走 API 29 路径，但该路径一旦出问题，用户会认为应用核心功能坏了。

**修复建议**：

- 对 API 29 单独处理 `RecoverableSecurityException`。
- 将 recoverable intent 暴露给 UI，由用户授权删除。
- 不要静默吞异常。
- 至少记录 URI、API level、异常类型和 message。
- API 30+ 继续使用 `MediaStore.createDeleteRequest()`。

**验收标准**：

- Android 10 真机或模拟器可以触发系统删除授权。
- 用户授权后照片能删除。
- 删除失败时有明确日志和 UI 反馈。

---

### P1-2：`deleteDirectly()` 批量失败语义不一致

**位置**：`deleteDirectly()`

**现状**：

循环中某一张删除失败时会设置 `allSuccess = false`，但循环仍继续处理后续照片。最后整体返回失败。实际行为是“部分继续执行，但结果只给整体失败”。

**风险**：

调用方无法知道哪些照片已经删了、哪些没删。UI 可能错误回滚，用户也无法理解删除结果。

**为什么是 P1**：

这会影响删除结果的一致性和可解释性，尤其是批量删除或恢复删除状态时。

**修复建议**：

二选一，必须明确语义：

1. **快速失败**：第一张失败就停止，返回失败和失败 URI。
2. **部分成功**：继续处理全部，返回成功列表、失败列表和失败原因。

对当前应用更推荐“部分成功结果对象”，因为照片删除本身就是逐张资源操作。

**验收标准**：

- 调用方可以知道每张照片的删除结果。
- UI 不会把部分成功误当成全部失败。
- 日志能定位失败 URI。

## P2 — 质量问题，建议修

### P2-1：`allowBackup="true"` 存在轻微隐私风险

**位置**：`AndroidManifest.xml`

**现状**：

Manifest 中允许备份。SharedPreferences 中保存了 `current_index`，可能通过 ADB 或系统备份恢复到其他设备。

**风险**：

风险不高，但对照片类应用来说，用户浏览位置也属于轻量隐私信息。

**修复建议**：

将 `android:allowBackup` 改为 `false`。

**验收标准**：

- Manifest 中 `android:allowBackup="false"`。
- 如有数据抽取规则，确认不会备份照片浏览状态。

---

### P2-2：字符串硬编码

**位置**：全项目 UI 文案

**现状**：

多处中文字符串直接写在 Kotlin/Compose 代码中，没有提取到 `strings.xml`。

**风险**：

不影响当前中文用户使用，但限制国际化，也会增加后续统一修改文案的成本。

**修复建议**：

- 将用户可见字符串迁移到 `res/values/strings.xml`。
- Compose 中使用 `stringResource()`。
- 暂不需要立即做多语言，但至少先建立资源化基础。

**验收标准**：

- 主要用户可见文案不再硬编码在 Kotlin 文件中。
- 构建通过。

---

### P2-3：删除路径没有测试覆盖

**位置**：`deleteDirectly()`、`MediaStore.createDeleteRequest()` 相关逻辑

**现状**：

API 29 的直接删除 / recoverable 删除路径，以及 API 30+ 的 delete request 路径缺少测试覆盖。

**风险**：

删除是最容易出现系统版本差异的路径，没有测试会导致后续重构时反复回归。

**修复建议**：

- 为删除结果语义增加单元测试。
- 为 API 分支选择增加测试。
- 对 API 29 的 recoverable 异常路径做 contract test。
- 对 API 30+ 的 createDeleteRequest 分支做 contract test。

**验收标准**：

- API 29 和 API 30+ 删除分支都有测试。
- 删除失败、部分成功、全部成功都有覆盖。

---

### P2-4：缩略图左边界无阻尼

**位置**：`SwipeStage`

**现状**：

左划到最后一张时 `dragX = 0f`，卡片完全不动，表现为硬边界。

**风险**：

不影响功能，但手感生硬。用户会感觉滑动突然失效。

**修复建议**：

- 最后一张继续允许少量拖动。
- 使用阻尼或回弹动画表达“已经到底”。
- 与 `docs/SWIPE_ANIMATION_V2.md` 中的动画设计保持一致。

**验收标准**：

- 最后一张左划时有轻微位移和回弹。
- 不触发下一张切换。
- 不破坏正常左右翻页动画。

## P3 — 可后续迭代

### P3-1：Coil 未配置缓存策略

**位置**：图片加载配置

**现状**：

目前依赖 Coil 默认缓存策略。

**风险**：

大图库、超大图、低内存设备上，默认配置可能不够稳，存在 OOM 或频繁解码风险。

**修复建议**：

- 明确配置 memory cache / disk cache。
- 限制加载尺寸，避免加载原图进内存。
- 对列表缩略图和大图使用不同尺寸请求。

**验收标准**：

- 大图库快速滑动时内存稳定。
- 缩略图不会加载不必要的大尺寸图片。

---

### P3-2：测试文件命名不一致

**位置**：`SwipeUpContractTest.kt`

**现状**：

文件名为 `SwipeUpContractTest.kt`，但类名是 `DeleteQueueContractTest`。

**风险**：

不影响功能，但会降低测试可读性和维护效率。

**修复建议**：

将文件名和类名统一。建议按实际测试主题命名为 `DeleteQueueContractTest.kt`。

**验收标准**：

- 文件名与类名一致。
- 测试仍可正常运行。

## 建议修复顺序

### 第一批：必须立即完成

1. 修复 `loadPhotos()` 异常处理。
2. 编写并发布隐私政策。
3. 修复 Android 10 删除路径。

这三项完成后，应用才具备基本上架条件。

### 第二批：发布前 hardening

4. 明确 `deleteDirectly()` 批量删除结果语义。
5. 关闭 `allowBackup`。
6. 补删除路径测试。

这批用于降低发布后出现核心功能回归的概率。

### 第三批：体验和维护优化

7. 字符串资源化。
8. 缩略图边界阻尼。
9. Coil 缓存策略。
10. 测试文件命名清理。

---

## 当前发布判断

当前版本还不建议直接上架。

最低上架门槛：

- P0-1 已修复并通过真机验证。
- P0-2 隐私政策 URL 已准备好并填入 Play Console。
- P1-1 Android 10 删除路径已验证，至少不能静默失败。

在这些完成之前，即使 APK 功能在某台真机上测试通过，也还不能认为具备稳定上架条件。
